# 安装、验证与回滚

本说明是手动操作清单，不自动修改服务。先在独立 CPA 实例验证，再安排生产更新；插件是宿主进程内本机代码，加载后拥有相应进程权限。

## 1. 核对宿主

- 确认 CPA 支持 C ABI 1 与 RPC schema 6，以及 auth/model/executor/quota/management 插件能力。
- 根据该 CPA 版本的配置文档核对 `plugins.enabled`、`plugins.dir`、`plugins.configs.fanzha`；不要猜测不同版本的配置兼容性。
- 检查实际扫描目录。常见布局是 `<plugins.dir>/linux/amd64/`，以宿主日志或当前插件安装情况为准。
- 确认管理 API 有强密钥、访问控制及可信 HTTPS。不要为安装插件而把管理 API 无鉴权暴露到公网。

## 2. 备份并替换

1. 在扫描目录之外备份旧 `.so`、CPA 配置与认证目录，认证备份按私密数据保护。
2. 对新二进制核对来源、架构、libc 要求及 SHA-256。
3. 先将新文件完整写入扫描目录之外的临时路径，再按你的部署流程原子替换；不要让扫描器读半个文件。
4. 扫描目录中同一插件只留一个活动版本，旧版和备份不能留在其中等待被同时加载。
5. 依据 `examples/plugin-config.yaml` 合并配置；`public_base_url` 是 CPA HTTPS origin，`upstream_url` 是真正接收账号令牌和消息的可信上游，两者不可混淆。
6. 用当前 CPA 明确支持的热重载机制加载；如果必须重启，先安排窗口。空 PATCH 或写回完全相同的配置可能不会触发 watcher。

默认从 Releases 下载 `install.sh` 后执行 `bash install.sh /你的插件扫描目录`；脚本下载已编译的 Linux amd64 成品并校验 SHA-256，无需 Go/GCC，要求 glibc 2.35 及以上。已有反诈插件时会拒绝覆盖，不修改配置或重启服务。自行构建使用 `bash scripts/build.sh`，再按上述步骤安装产物。

## 3. 无聊天验证

- 检查插件 registered 状态、版本 `0.2.5-rewrite`、仓库地址与四个模型名。
- 在你自己的 CPA HTTPS 域名打开 `/v0/resource/plugins/fanzha/login` 和 `/v0/resource/plugins/fanzha/quota`。
- 填写自己的管理密钥；公开资源页不能包含账号令牌。管理数据 API 必须由 CPA 鉴权保护。
- 查询一次额度；查询本身不发聊天请求，仍须避免高频请求。
- 旧 `type: fanzha` 文件应保留账号文件名、ID、自定义字段。遇到 401/403 先检查管理鉴权和上游账号状态，不批量反复尝试。

独立额度页不需要修改 CPA 主面板。某些面板版本误调用 `/v8/management/quota/fetch`；应核对对应宿主实际提供的接口，而不是修改本插件去假冒不存在的 CPA 核心路由。本仓库不分发修改过的官方管理面板。

## 4. 一次可选聊天验证

明确同意消耗额度后，用已配置的聊天客户端发一次请求。核对增量文本、最后的 `finish_reason: stop`、宿主生成的 `[DONE]` 和额度变化。不要在失败后无限自动重试；认证成功不意味着账号有可用额度。

## 5. 回滚

- 如果注册失败、模型丢失或旧账号异常，先停止进一步请求。
- 在扫描目录之外保留失败产物用于审查，恢复备份的旧 `.so` 和必要配置，确保只加载一个版本。
- 按同样的宿主流程重载并验证原模型、账号索引与额度页。
- 不要以新建凭据、删认证目录或更换其他插件来掩盖回归。令牌若已在上游轮换，磁盘旧副本未必仍有效；回滚二进制不会撤销上游状态变化。

## 已知路径限制

页面和登录回调使用域名根路径，不保证反向代理子路径部署可用。推荐为 CPA 分配独立 HTTPS 域名；需要子路径时应先修改 URL 处理并补充测试。不要承诺只改 `public_base_url` 就能支持任意代理前缀。
